# 第二版搜索质量升级计划

## 1. 文档用途

本文是交给后续 Agent 独立实施的主计划。后续设计、编码、测试、集成验证、文档更新和发布准备均由接手 Agent 完成，不依赖原计划编写者继续验收。

“第二版”在本文中表示当前 `0.1.x` 之后的下一轮质量升级。建议发布版本为 `0.2.0`；如果维护者希望使用 `2.0.0`，只调整版本号，不扩大本文范围。

实施原则：

- 以当前项目为代码基线，以 `_references/dsh-free-search` 为行为和故障经验参考；
- 优先做不增加请求次数、不会扩大权限的高收益改进；
- 每一批都必须可以独立完成、独立测试、独立交付；
- 完成第一批后即可停止并发布，不要求为了“第二版”一次做完全部批次；
- 保持 DSH 原生 `web_search` provider，不注册自定义搜索工具；
- 不注册、不选择、不修改 `web_fetch` provider。

## 2. 开始前必须遵循

接手 Agent 开始任何操作前必须完整读取：

1. 项目根目录 `AGENTS.md`；
2. `E:\Projects\Python\PythonWorkspace\Project_DeepSeekHarness\README.md`；

4. `docs/architecture.md`、`docs/security.md`、`docs/verification.md`；
5. 按需阅读 `_references/dsh-free-search` 中本文列出的参考文件。

不得操作真实 `desktop` Profile。需要 DSH 集成验证时，只使用隔离的 `plugin-dev` Profile，并严格遵守 Windows Junction 安全规则。不得执行参考仓库的脚本，不得安装或启用参考插件。

如果产生 Git commit，commit message 必须附带项目 `AGENTS.md` 要求的 Agent、具体模型名称和带时区时间戳。

## 3. 总目标

在继续只使用 Bing 和 DuckDuckGo 公共 HTML 入口的前提下，以尽可能小的实现成本改善：

- 结果相关性；
- 重复结果比例；
- 首屏域名多样性；
- 中文、英文查询的市场适配；
- Bing 空结果页、缓存错页和结构漂移时的降级行为；
- 免费入口出现短暂故障时的总体可用性。

本轮不追求“引擎数量”，也不追求研究代理、正文抓取或 LLM 重排。

## 4. 明确不做

以下内容不属于本计划，后续 Agent 不得顺手加入：

- 第三个搜索引擎、SearXNG、自定义 endpoint；
- API key、凭据、代理、Cookie 或任意请求头配置；
- `web_fetch` provider 或网页正文抓取；
- `advanced_search`、`multi_search`、平台搜索等自定义工具；
- LLM 查询改写、LLM 摘要、向量嵌入或付费 reranker；
- 本地 HTTP bridge、子进程、浏览器、文件缓存或遥测；
- 自动更新检查；
- 大规模重写设置 UI；
- 硬编码“内容农场”黑名单；如未来需要，应作为用户显式配置的独立功能评估。

DSH 核心已经支持一次 `web_search` 提交多个查询并负责并发、去重和 round-robin 合并；provider 不应重复实现查询拆分或改写。

## 5. 推荐批次

### 第一批：单引擎结果质量快修（必须做，完成后即可发布）

目标：不增加搜索引擎请求次数，不改变查询向哪些服务发送，只改善单次响应的质量。

#### 5.1 自动语言与 Bing 市场策略

当前实现默认始终发送 `mkt=zh-CN`。参考实现记录了部分网络线路下该参数会让 Bing 返回空 SERP 的实际问题。

实施要求：

- 给 `market` 增加 `auto`，并将新默认值改为 `auto`；
- `auto` 下根据查询是否包含 CJK 字符选择 `Accept-Language`；
- `auto` 下不向 Bing 发送 `mkt`，让 Bing 结合查询和请求语言自行判断；
- 用户显式选择 `zh-CN` 或 `en-US` 时，保持发送对应 `mkt`；
- DuckDuckGo 的 `kl` 同样根据自动识别结果选择；
- 不做复杂语言识别，只使用确定性的 CJK 检测。

预计涉及：

- `lib/provider.js`
- `lib/network.js`
- `lib/index.js`
- `src/client/settings-card.jsx`
- `locale/zh.json`
- `locale/en.json`
- 配置和网络相关测试

#### 5.2 Bing 错页相关性保护

Bing 可能返回结构正常但与查询无关的缓存页。仅判断是否存在 `b_algo` 不足以保证结果可用。

实施要求：

- 提取轻量、纯函数的查询 token 生成逻辑；
- CJK 连续文本使用一至二字 token，拉丁字母和数字使用长度不小于 2 的词；
- 检查全部候选结果的标题、摘要和 URL 是否至少存在查询 token 重叠；
- 完全无重叠时将本次结果判定为引擎空结果/无关结果，从而进入现有 fallback；
- 纯符号、无法产生 token 的查询不拦截；
- 该规则只用于识别明显错页，不作为通用相关性打分器，不重排正常结果。

建议将纯函数放入新模块，例如 `lib/relevance.js`，避免继续扩大解析器职责。

#### 5.3 候选超采样与安全去重

当前网络请求、解析和最终返回都使用同一个 `maxResults`，过滤危险 URL 或重复项后没有候选补位。

实施要求：

- 内部候选数量采用 `min(max(maxResults * 2, maxResults), 20)`；
- Bing 的 `count` 使用内部候选数量；
- 解析器先产生较多候选，再统一清洗、去重、排序并截断到请求上限；
- 只移除明确无歧义的跟踪参数，例如 `utm_*`、`gclid`、`fbclid`、`msclkid`、`spm`、`vd_source`；
- 必须保留可能标识资源的参数，例如 `id`、`q`、`page`、`v`、`lang`、`type`、`from`；
- URL fragment 不参与去重；返回给模型的 URL 也应去掉 fragment 和上述跟踪参数；
- 归一化必须幂等，非法 URL 继续被现有 HTTP(S) 校验丢弃。

建议将跟踪参数清单作为导出常量，便于测试和安全审计。

#### 5.4 首屏域名多样性

不引入复杂评分模型，只做确定性重排：

- 以可注册域近似值分组；
- 常见二级公共后缀至少覆盖 `com.cn`、`com.hk`、`com.tw`、`co.jp`、`co.kr`、`co.uk`、`com.au`；
- 保留每个域名组内的原始结果顺序；
- 按组轮转输出，使前几条尽量来自不同站点；
- 只重排，不删除同域结果；候选不足时仍可返回同域后续结果；
- 不把“多个引擎都返回该 URL”解释为可信度证明。

建议放入新模块，例如 `lib/ranking.js`。

#### 5.5 第一批完成定义

第一批只有在以下条件全部满足时才算完成：

- `npm test` 全部通过；
- 新增测试覆盖自动市场、显式市场、Bing 明显错页、纯符号查询、超采样上限、跟踪参数剥离、资源参数保留、域名轮转和结果最终上限；
- 原有安全测试、响应体限制、重定向限制和 abort 行为不回退；
- `npm pack --dry-run` 不包含 `_references/`、测试输出、日志或 Profile 内容；
- README 中英文版、配置表、架构文档和验证文档同步更新；
- `THIRD_PARTY_NOTICES.md` 对实质改编的参考代码保持准确 attribution；
- 未触碰任何真实 `desktop` Profile；
- Git working tree 中不存在临时包、日志和测试输出。

完成以上内容后，可以直接发布 `0.2.0`，无需继续第二批。

### 第二批：按需双引擎融合（推荐，但独立可选）

目标：只有在单引擎结果不足时才付出第二次请求成本，避免默认并发请求两个服务。

#### 5.6 配置语义

优先选择一个新枚举替代继续堆叠布尔开关：

- `fast`：首选引擎成功即返回；失败时是否回退沿用现有 `fallback`；
- `balanced`：首选失败、明显错页，或清洗后结果少于请求数量时，串行请求备用引擎并融合；
- `deep`：两个引擎并发请求并融合。

为控制范围，第二批可以只实现 `fast` 和 `balanced`；`deep` 可留到后续。若只实现两档，配置名仍应允许以后自然增加第三档。

隐私要求：

- 设置界面和中英文 README 必须明确说明 `balanced` 可能把同一查询发送给两个搜索引擎；
- 不得在升级后静默改变既有用户的查询发送范围；
- 如果无法可靠迁移旧配置，则默认保持 `fast`，由用户显式选择 `balanced`；
- 不得用“提升质量”作为隐瞒额外查询发送的理由。

#### 5.7 融合算法

保持算法简单：

1. 每个引擎保留自己的原始排名；
2. 用第一批的规范化 URL 去重；
3. 同一 URL 在两个引擎出现时，合并缺失的标题、摘要和发布时间，不重复返回；
4. 按结果名次在引擎之间 round-robin；
5. 再应用域名多样性轮转；
6. 最后截断到 `maxResults`。

不引入 LLM、embedding、外部 reranker 或难以解释的手工“权威域名分数”。如果要使用 RRF，只能作为等价、可测试的纯函数实现，并且不得让重复命中次数压过域名多样性。

#### 5.8 第二批完成定义

- 两个引擎的成功、一个失败、两个失败、一个空结果、调用方取消、生命周期取消均有测试；
- `balanced` 在首选结果已经充足时不得调用备用引擎；
- 融合后无规范化 URL 重复，且不超过 `maxResults`；
- 并发或串行请求均共享调用方 abort；
- 日志只记录实际使用的引擎和稳定错误码，不记录查询正文或响应正文；
- 中英文配置说明明确披露查询可能发送给两个服务；
- 完成隔离 `plugin-dev` 的正式 `web_search` Host smoke test。

### 第三批：可靠性增强（可选，质量目标达成后再决定）

本批主要改善稳定性和延迟，不是第二版发布的前置条件。

候选内容：

- 失败分类：反爬/限流、网络/5xx、结构变化、超时；
- 反爬或 429 后 60 秒内存冷却，不立即重复撞同一引擎；
- 普通网络或 5xx 在总预算内最多重试一次；
- 一次搜索共用总预算，避免两个引擎各自消耗完整超时；
- 最多 50 条、1 至 5 分钟的内存 LRU 缓存；
- 回退引擎结果使用较短 TTL，避免首选恢复后长期命中回退缓存；
- 只记录错误类别、引擎、耗时和结果数量，不记录查询正文。

第三批不得引入磁盘缓存、遥测或后台网络任务。所有 timer、缓存和冷却状态必须随插件 dispose 清理或自然失效。

## 6. 轻量评测策略

本轮不先建设大型人工标注系统。采用以下最小评测组合：

### 6.1 必须具备的离线测试

- 当前 Bing、DuckDuckGo fixture；
- Bing 明显无关缓存页 fixture；
- 同一 URL 带/不带跟踪参数；
- 同域名大量占位；
- 中英文、混合文字、纯符号查询；
- 两个引擎部分重复、字段互补的融合结果。

fixture 必须脱敏、体积有界，只用于开发测试，不在安装或运行时联网更新。

### 6.2 可选 live smoke

在现有环境变量开关下保留 live test，不让默认 `npm test` 访问网络。固定查询建议不超过 6 条：

- `DeepSeek Harness`
- 一个中文官方网站查询；
- 一个英文技术文档查询；
- 一个中英文混合产品名；
- 一个不存在或极冷门的查询；
- 一个容易产生同域重复的查询。

live smoke 只验证非空、URL 合法、结果上限、无明显重复和取消行为，不把公共搜索排名写成脆弱的精确断言。

## 8. Agent 分工建议

如果由多个 Agent 执行，推荐按批次或模块分工，不要多人同时改同一文件：

1. Agent A：第一批实现与单元测试；
2. Agent B：第一批代码审查、安全边界检查、中英文文档和发布包检查；
3. Agent C：仅在第一批完成后实施第二批；
4. Agent D：第二批集成验证、回归和最终发布准备。

若只有一个 Agent，严格按第一批 → 自验收 → 决定是否继续第二批的顺序执行。不要同时铺开三个批次。

## 10. 最终停止条件

满足以下任一条件即可结束第二版工作：

1. 第一批全部完成并通过其完成定义；
2. 第一、二批全部完成并通过各自完成定义；
3. 后续维护者明确决定停止扩展，并且已完成部分可以独立通过测试和文档验收。

第三批不是发布门槛。不得因为计划中还存在可选项，就把已经完成且有明确质量收益的第一批长期滞留。
